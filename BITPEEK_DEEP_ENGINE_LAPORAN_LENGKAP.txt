03. TAGGED HASH DAN ARITMETIKA SECP256K1
===============================================================================

3.1 taggedHash

Signature:
  taggedHash(tag: string, ...messages: (Uint8Array | string)[]): Uint8Array

Proses:
  tagHash = SHA256(UTF8(tag))
  hasil   = SHA256(tagHash || tagHash || message1 || message2 || ...)

Output selalu 32 byte. String message dikonversi ke UTF-8; Uint8Array digunakan
sebagai byte mentah. Penggabungan dilakukan melalui update() pada Sha256,
sehingga tidak perlu membuat satu buffer gabungan besar. Tidak ada cache tag
hash baru; tag hash dihitung langsung setiap pemanggilan.

Pengujian memakai SHA-256 native Node.js sebagai pembanding untuk input kosong,
string Unicode, input campuran string/byte, dan pesan yang melewati satu blok.

3.2 Representasi dan domain kurva

  type Point = { x: bigint; y: bigint } | null

null merepresentasikan titik infinity. Implementasi memakai koordinat affine.
Persamaan kurva adalah y^2 = x^3 + 7 (mod p).

  p = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEFFFFFC2F
  n = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141

Konstanta generator GX dan GY yang sudah ada tetap digunakan.

3.3 Operasi yang tersedia

  pointAdd(left: Point, right: Point): Point
  pointDouble(point: Point): Point
  scalarMul(scalar: bigint, point: Point): Point
  liftX(bytes: Uint8Array): Point

Keempatnya tersedia sebagai fungsi export dan method static Secp256k1Engine.

pointAdd:
  - Infinity menjadi elemen identitas.
  - Titik identik menggunakan pointDouble.
  - Titik dengan X sama dan Y berlawanan menghasilkan infinity.
  - Kasus umum memakai slope (y2-y1)/(x2-x1) di field modulo p.

pointDouble:
  - Infinity atau Y=0 menghasilkan infinity.
  - Slope adalah 3*x^2/(2*y), dengan operasi field modulo p.

scalarMul:
  - Scalar dinormalisasi ke [0, n-1], termasuk scalar negatif.
  - Menggunakan metode double-and-add.
  - Scalar 0 atau kelipatan n menghasilkan infinity.

liftX:
  - Input harus tepat 32 byte big-endian.
  - Menolak X >= p.
  - Memakai sqrtModP yang sudah ada untuk akar x^3+7.
  - Menolak X yang tidak menghasilkan titik kurva.
  - Memilih Y genap, sesuai representasi x-only BIP-340.

Modular inverse menggunakan extended Euclidean algorithm. Fungsi operasi titik
mengasumsikan koordinat input adalah titik kurva yang valid; verifyDLEQ melakukan
pemeriksaan titik pada batas API sebelum menggunakan operasi tersebut.

04. VERIFIKASI SCHNORR BIP-340
===============================================================================

Signature:
  Secp256k1Engine.verifySchnorr(
    pubkey32: Uint8Array,
    msg32: Uint8Array,
    sig64: Uint8Array
  ): { valid: boolean; reason?: string }

Input:
  public key : 32 byte x-only
  message    : tepat 32 byte
  signature  : tepat 64 byte, r || s

Urutan verifikasi:
1. Validasi panjang input.
2. Lift public key menjadi titik P dengan Y genap.
3. Parse r dan s sebagai unsigned big-endian.
4. Tolak r >= p dan s >= n; keduanya tidak direduksi agar menjadi valid.
5. Hitung e = int(taggedHash('BIP0340/challenge', rBytes, pubkey, msg)) mod n.
6. Hitung R = s*G + (n-e)*P.
7. Tolak infinity, Y ganjil, atau R.x yang berbeda dengan r.
8. Kembalikan { valid: true } jika seluruh pemeriksaan lulus.

Alasan penolakan yang dapat dikembalikan:
  Public key must contain exactly 32 bytes
  Message must contain exactly 32 bytes
  Schnorr signature must contain exactly 64 bytes
  Invalid public key X coordinate
  r >= p
  s >= n
  R is infinity
  R has odd Y coordinate
  Signature verification equation failed (Rx != r)

Kontrak API ini sengaja mensyaratkan message 32 byte sesuai directive. Signature
Bitcoin 65 byte yang membawa sighash byte tidak diterima langsung oleh method
ini; caller harus menyiapkan signature 64 byte dan message yang sesuai.

05. VERIFIKASI DLEQ BIP-374 DAN HUBUNGANNYA DENGAN BIP-375
===============================================================================

Signature:
  Secp256k1Engine.verifyDLEQ(
    G1: Point, P1: Point, G2: Point, P2: Point,
    proof64: Uint8Array,
    message?: Uint8Array
  ): { valid: boolean; reason?: string }

Pernyataan yang diperiksa adalah log_G1(P1) = log_G2(P2).

Pemetaan nama ke BIP-374:
  G1 = G, generator pertama
  P1 = A, public point pertama
  G2 = B, generator kedua
  P2 = C, public point kedua / ECDH share

proof adalah e || s, masing-masing 32 byte. Optional message, bila diberikan,
harus tepat 32 byte. Tidak diberikan berarti transcript memakai message kosong.

Urutan verifikasi:
1. Validasi panjang proof dan optional message.
2. Pastikan G1, P1, G2, P2 adalah titik finite pada kurva secp256k1.
   Koordinat harus bigint, non-negatif, kurang dari p, dan memenuhi kurva.
3. Parse e dan s; tolak e >= n atau s >= n.
4. Hitung R1 = s*G1 - e*P1 dan R2 = s*G2 - e*P2.
5. Tolak R1 atau R2 yang infinity.
6. Serialisasi titik dengan encoding SEC compressed 33 byte, termasuk Y parity.
7. Hitung challenge dengan urutan transcript berikut:

   expectedE = int(taggedHash('BIP0374/challenge',
                 cbytes(P1), cbytes(G2), cbytes(P2), cbytes(G1),
                 cbytes(R1), cbytes(R2), optionalMessageOrEmpty)) mod n

8. Verifikasi expectedE == e.

Alasan penolakan:
  DLEQ proof must contain exactly 64 bytes
  DLEQ message must contain exactly 32 bytes
  G1/P1/G2/P2 must be a finite point on secp256k1
  e >= n
  s >= n
  R1 is infinity
  R2 is infinity
  DLEQ challenge verification failed

BIP-375 memakai proof BIP-374 untuk memverifikasi Silent Payment ECDH shares.
Method ini memverifikasi proof dan titik yang sudah diekstrak oleh caller.
Cakupan ini tidak mencakup parser PSBT BIP-375, eligibility input, penyusunan
output Silent Payments, atau validasi keseluruhan transaksi/PSBT.

06. VERIFIKASI TAPROOT BIP-341
===============================================================================

Signature:
  Secp256k1Engine.verifyTaprootTweak(
    internalKey32: Uint8Array,
    outputKey32: Uint8Array,
    merkleRoot?: Uint8Array
  ): { valid: boolean; parity: number; reason?: string }

Input internal key dan output key harus tepat 32 byte x-only. Optional Merkle
root harus tepat 32 byte jika diberikan. Untuk key-only tweak, omit merkleRoot;
Uint8Array(0) yang diberikan eksplisit ditolak sebagai root dengan panjang salah.

Urutan verifikasi:
1. Lift internal key menjadi P dengan Y genap.
2. Tolak output X >= p.
3. Hitung t = int(taggedHash('TapTweak', internalKey, merkleRootOrEmpty)).
4. Tolak t >= n.
5. Hitung Q = P + t*G; tolak Q infinity.
6. parity = Q.y mod 2.
7. Verifikasi Q.x sama dengan output key.

Mengapa t >= n ditolak:
Directive menuliskan t modulo n, tetapi aturan verifikasi BIP-341 mewajibkan
penolakan overflow. Mengurangi t sebelum memeriksa batas akan menerima tweak
yang seharusnya ditolak oleh standar. Implementasi mengikuti pemeriksaan batas
BIP-341 ini, dan terdapat tes khusus untuk overflow.

Nilai parity:
  0 atau 1 : parity Q berhasil dihitung; tersedia juga saat output X mismatch.
  -1       : verifikasi gagal sebelum titik Q yang valid tersedia.

Alasan penolakan:
  Internal and output keys must contain exactly 32 bytes
  Merkle root must contain exactly 32 bytes when supplied
  Invalid internal key X coordinate
  Output key X coordinate >= p
  Taproot tweak >= n
  Tweaked point is infinity
  Taproot output key mismatch

MCP menyediakan expectedParity tambahan untuk memeriksa parity 0/1 terhadap
hasil method ini. Jika berbeda, reason menjadi Taproot output Y parity mismatch.

07. AUDIT CONSTANT-TIME DAN PERLUASAN DISASSEMBLER
===============================================================================

7.1 API

  ConstantTimeAuditor.auditX86_64(instructions, options = {})
  ConstantTimeAuditor.auditARM64(instructions, options = {})
  ConstantTimeAuditor.auditBytes(code, options)

  ConstantTimeAuditOptions:
    checkMemoryLookups?: boolean      default efektif true

auditBytes menerima DisassemblyOptions yang sudah ada, ditambah opsi memory:
  arch: 'x86_64' | 'aarch64'
  baseAddress?: bigint
  maxInstructions?: number
  checkMemoryLookups?: boolean

7.2 Bentuk hasil core

  {
    hasConditionalBranches: boolean,
    branchCount: number,
    hasCacheTimingHazards: boolean,
    hasVariableLatencyHazards: boolean,
    suspiciousInstructions: Array<{ offset, mnemonic, reason }>,
    hazards: Array<{ offset, mnemonic, operands?, severity, category, reason }>,
    isCleanConstantTime: boolean
  }

offset adalah byte offset relatif terhadap awal region yang diaudit. Pada stream
instruksi yang diberikan langsung, offset dihitung dari jumlah instruction.length.
Satu instruksi dapat menghasilkan beberapa hazard dengan offset yang sama.
branchCount menghitung instruksi conditional branch, bukan total hazard.

7.3 Kategori dan severity

  BRANCH           CRITICAL  Conditional jump/branch yang mungkin terkait secret.
  CACHE_TIMING     HIGH      Indexed memory operand / potensi table lookup.
  VARIABLE_LATENCY HIGH      Division atau repeated string operation.
  VARIABLE_LATENCY WARN      Bit scan, register-controlled shift/rotate, ARM bit op.
  UNDECODED        WARN      Instruksi unknown/truncated, metadata tidak cocok,
                             atau byte tersisa akibat batas instruksi.

Klasifikasi menyatakan pola yang perlu diperiksa. Auditor tidak melakukan
analisis aliran secret atau membuktikan bahwa operand berasal dari secret.

7.4 Indexed memory

x86_64: memeriksa isi [...] untuk beberapa register atau scaled index '*'.
Contoh ditandai HIGH:
  mov rax, [rbx + rcx*8]
  mov rax, [rax + rbx]
  mov eax, [rsi + rdx]
  mov rax, [rsp + rax*4]

Contoh tanpa cache hazard dari aturan ini:
  mov rax, [rbp - 16]
  mov rax, [rsp + 8]
  mov rax, [rip + 0x100]
  mov rax, [rdi]
  mov rax, [0x1000]

LEA dikecualikan karena menghitung alamat tanpa mengakses memory. Deteksi x86
memory ini memakai format bracket Intel; ia bukan parser umum memory AT&T.

AArch64: register offset, termasuk scaled/extended register, ditandai HIGH:
  ldr x0, [x1, x2]
  ldr x0, [x1, x2, lsl #3]
  ldr w0, [sp, w2, uxtw #2]

Immediate/fixed offset dan xzr/wzr tidak diperlakukan sebagai variable index.
checkMemoryLookups=false hanya mematikan kategori CACHE_TIMING; branch,
variable latency, dan undecoded inspection tetap berjalan.

7.5 Variable latency

x86_64:
  - DIV/IDIV dan variasi suffix ukuran.
  - BSF/BSR.
  - SHL/SAL/SHR/SAR/ROL/ROR dengan count register.
  - Penulisan count Intel 'rax, cl' dan AT&T '%cl, %rax' dikenali.
  - Shift immediate seperti 'rax, 3' atau '$3, %rax' tidak ditandai.
  - REP MOVS dan REP STOS.

AArch64:
  - UDIV/SDIV.
  - LSLV/LSRV/ASRV/RORV.
  - Alias LSL/LSR/ASR/ROR dengan operand count register.
  - CLZ/CLS/RBIT pada stream mnemonic yang disediakan caller.

Timing aktual bergantung pada instruksi dan prosesor. Temuan WARN pada bit/shift
merupakan permintaan review timing prosesor, bukan pengukuran latency.

7.6 Mengapa disassembler ikut diubah

Operand placeholder seperti modrm(0x..) tidak cukup untuk mendeteksi memory
index. Decoder sekarang menghasilkan konteks seperti 'rax, [rbx + rcx*8]'.

Cakupan tambahan x86 byte decoder:
  - MOV register/memory opcode 88, 89, 8A, 8B.
  - Operand register 8/16/32/64 bit dan register tambahan melalui REX.
  - ModRM, SIB, base/index/scale, displacement 8/32 bit, RIP-relative.
  - Shift/rotate opcode D0-D3 dan C0-C1 untuk bentuk yang didukung.
  - BSF/BSR opcode 0F BC / 0F BD.
  - REP MOVS/STOS, termasuk prefix ukuran operand pada subset yang ditambahkan.
  - Operand nyata untuk division dan bentuk ALU64 immediate yang sudah didukung.

Cakupan tambahan AArch64 byte decoder:
  - LSLV/LSRV/ASRV/RORV.
  - Integer register-offset load/store dengan extend/shift yang didukung.
  - Reserved combinations yang tidak didukung tidak dianggap instruksi valid.

CLZ/CLS/RBIT dikenali oleh auditor pada supplied mnemonic stream; perluasan byte
decoder ini tidak menambahkan decoding opcode ketiganya. Opcode yang belum
didukung tetap menghasilkan UNDECODED, sehingga hasil audit tidak clean.

7.7 Kondisi fail-closed

Instruksi unknown/truncated, arsitektur berbeda, byte span berbeda dengan length,
atau byte yang tidak diperiksa akibat instruction budget menghasilkan hazard.
isCleanConstantTime hanya true jika ada instruksi dan tidak ada temuan.
Length nonpositif/pecahan/tidak aman dan akumulasi offset yang melampaui safe
integer menyebabkan RangeError, agar lokasi temuan tidak diam-diam rusak.

08. KONTRAK PARAMETER DAN HASIL MCP
===============================================================================

8.1 Sumber input bersama

Gunakan tepat salah satu:
  rawHex : string hex byte yang akan diaudit.
  handle : session yang dikembalikan bitpeek_open.

offset dan length hanya boleh dipakai bersama handle. offset default 0.
Path session divalidasi kembali melalui security manager. Ukuran file yang
berubah sejak session dibuka menyebabkan SOURCE_CHANGED. Range tidak boleh
melewati file atau melampaui batas ukuran tool.

source pada hasil berisi:
  kind: 'hex' | 'session'
  length: jumlah byte input yang dibaca
  sha256: hash input utama
  handle dan offset: hanya untuk sumber session

8.2 bitpeek_constant_time_audit

Parameter tambahan:
  arch                'x86_64' atau 'aarch64'; default 'x86_64'
  checkMemoryLookups  boolean; default true; null/string/angka ditolak
  maxInstructions     integer 1..10000; default 10000
  baseAddress         string unsigned 64-bit, hexadecimal atau decimal

Batas input: 65536 byte. Jika memakai handle tanpa length, tool membaca hingga
256 byte pertama yang tersedia setelah offset. Untuk inline hex, seluruh input
yang diberikan diperiksa sampai batas instruksi.

baseAddress default adalah offset file untuk session, atau nol untuk inline hex.
Alamat yang keluar dari range unsigned 64-bit ditolak.

Field tambahan MCP pada hasil core:
  arch, baseAddress, source, checkMemoryLookups, summary
  verificationScope: 'static-instruction-patterns'
  constantTimeProven: false

Setiap hazard dan suspiciousInstruction diberi:
  address    = baseAddress + offset, sebagai string hexadecimal
  fileOffset = source.offset + offset, hanya jika input dari session

Alamat besar tidak dipersempit menjadi Number; perhitungan memakai BigInt.

8.3 bitpeek_secp256k1_audit

Batas input utama: 1 MiB / 1048576 byte. Jika memakai handle tanpa length,
default membaca seluruh sisa file; caller harus memilih range jika lebih besar.

Format lama tetap tersedia:
  auto, pubkey, der, compact, bitcoin-tx

Format baru dan arti rawHex atau byte range:

  format              Input utama         Parameter companion
  ------------------  ------------------  ------------------------------------
  bip340-schnorr      signature 64 byte   pubkeyHex, messageHex wajib
  dleq                proof 64 byte       g1Hex, p1Hex, g2Hex, p2Hex wajib;
                                          messageHex optional
  taproot-tweak       output key 32 byte  internalKeyHex wajib;
                                          merkleRootHex, expectedParity optional

pubkeyHex/internalKeyHex adalah x-only 32 byte. messageHex/merkleRootHex juga
32 byte jika diberikan. expectedParity hanya boleh angka 0 atau 1.

g1Hex/p1Hex/g2Hex/p2Hex menerima public key SEC compressed 33 byte atau
uncompressed 65 byte. DLEQ menolak x-only karena proof harus mempertahankan
Y parity. Point yang gagal validasi encoding atau kurva ditolak sebagai input.

Argument tidak dikenal atau companion yang tidak sesuai format ditolak.
Contoh: messageHex pada format pubkey, atau g1Hex pada bip340-schnorr.

8.4 Hasil verifikasi dan error

Format verifikasi baru mengembalikan:
  format, valid, status: 'PASS' | 'FAIL', source,
  verificationScope: 'cryptographic-verification',
  cryptographicSignaturesVerified, summary,
  reason jika gagal, parity untuk Taproot.

cryptographicSignaturesVerified true hanya untuk Schnorr yang valid.
Field tersebut false pada DLEQ dan Taproot, karena keduanya bukan pemeriksaan
signature Schnorr; keberhasilannya dibaca dari valid dan status.

Signature/proof/tweak yang gagal verifikasi menjadi hasil audit FAIL dengan
alasan, bukan error pemanggilan MCP. Argument tidak lengkap, encoding companion
invalid, range salah, atau session tidak diizinkan menjadi error MCP.

Payload JSON yang sama dikirim melalui structuredContent dan content teks.
Tool tetap memiliki readOnlyHint=true, destructiveHint=false,
idempotentHint=true, dan openWorldHint=false.

2. Secp256k1 Point Arithmetic in `packages/core/src/bchain/secp256k1.ts`:
   Curve: y^2 = x^3 + 7 over F_p.
   Implement pure BigInt projective or affine point operations (verification only,
   constant-time is not required in TS verification, but mathematical correctness is mandatory):
   - `Point = { x: bigint; y: bigint } | null` (null represents infinity).
   - `pointAdd(P: Point, Q: Point): Point`
   - `pointDouble(P: Point): Point`
   - `scalarMul(k: bigint, P: Point): Point` (k modulo n)
   - `liftX(xBytes: Uint8Array): { x: bigint; y: bigint } | null`:
     Parse 32-byte big-endian $x$.
     If $x \ge p$, return null.
     Compute $y^2 = (x^3 + 7) \pmod p$.
     Compute $y = \text{sqrtModP}(y^2)$. If null, return null.
     If $y \pmod 2 \ne 0$, $y = p - y$ (ensure even Y per BIP-340).
     Return `{ x, y }`.

3. BIP-340 Schnorr Verification:
   Add method to `Secp256k1Engine`:
   ```typescript
   public static verifySchnorr(
     pubkey32: Uint8Array,
     msg32: Uint8Array,
     sig64: Uint8Array
   ): { valid: boolean; reason?: string }
   ```
   Verification Steps:
   - Check lengths: pubkey32 must be 32 bytes, msg32 must be 32 bytes, sig64 must be 64 bytes.
   - $P = \text{liftX}(pubkey32)$. If null, return `{ valid: false, reason: 'Invalid public key X coordinate' }`.
   - $r = \text{unsignedBigEndian}(sig[0..32])$. If $r \ge p$, return `{ valid: false, reason: 'r >= p' }`.
   - $s = \text{unsignedBigEndian}(sig[32..64])$. If $s \ge n$, return `{ valid: false, reason: 's >= n' }`.
   - $e = \text{unsignedBigEndian}(\text{taggedHash}('BIP0340/challenge', sig.subarray(0, 32), pubkey32, msg32)) \pmod n$.
   - Compute $R = s \cdot G - e \cdot P = s \cdot G + (n - e) \cdot P$.
   - If $R == \text{null}$ (infinity), return `{ valid: false, reason: 'R is infinity' }`.
   - If $R.y \pmod 2 \ne 0$ (odd Y), return `{ valid: false, reason: 'R has odd Y coordinate' }`.
   - If $R.x \ne r$, return `{ valid: false, reason: 'Signature verification equation failed (Rx != r)' }`.
   - Return `{ valid: true }`.

4. BIP-374 DLEQ Proof Verification (Silent Payments Hardware Wallet Support):
   Add method to `Secp256k1Engine`:
   ```typescript
   public static verifyDLEQ(
     G1: { x: bigint; y: bigint },
     P1: { x: bigint; y: bigint },
     G2: { x: bigint; y: bigint },
     P2: { x: bigint; y: bigint },
     proof64: Uint8Array
   ): { valid: boolean; reason?: string }
   ```
   Verifies that $\log_{G_1}(P_1) == \log_{G_2}(P_2)$.
   Proof contains challenge $e$ (32 bytes) and scalar $s$ (32 bytes).
   Computes $R_1 = s \cdot G_1 - e \cdot P_1$ and $R_2 = s \cdot G_2 - e \cdot P_2$.
   Verifies challenge equation according to BIP-374 specification.

5. BIP-341 Taproot Tweak Verification:
   Add method:
